# X 用户媒体下载器设计

## 目标

制作一个 Manifest V3 Chrome 扩展。用户在已登录的 X（`x.com` 或 `twitter.com`）用户主页中，手动从最新内容滚动到最早内容时，扩展持续采集该用户可见推文里的图片和视频，并在采集结束后按原图和最高可用 MP4 版本下载。

首版只处理用户当前账号实际有权限访问的内容；不使用 X API，也不上传数据。

## 用户流程

1. 用户打开 `x.com/<用户名>` 的帖子页。
2. 在扩展弹窗选择是否包含转推、是否包含回复，然后点击“开始采集”。
3. 扩展要求刷新一次页面，以保证首屏推文的网络数据也能采集；刷新后任务自动恢复为采集状态。
4. 用户手动向下滚动，直到 X 不再加载更早内容。内容脚本实时记录每个新出现的推文和媒体。
5. 用户点击“停止并下载”。弹窗显示采集总数、可下载数量和不可下载视频数量，并开始下载队列。
6. 用户可暂停、恢复或重试失败项；重新打开浏览器后，进入同一用户主页可恢复未完成任务。
7. 若选择包含回复，用户进入回复页并按相同流程采集。转推在帖子流中根据开关筛选。

## 文件结构和命名

浏览器默认下载目录下按用户名创建目录，媒体直接平铺：

```text
<用户名>/
  2026-08-16_14-32-05_01.jpg
  2026-08-16_14-32-05_02.jpg
  2026-08-16_14-32-05_03.mp4
```

文件名格式为 `<发布日期>_<时-分-秒>_<该推文媒体序号>.<扩展名>`。若不同推文同一秒内产生同名，追加内部冲突序号以避免覆盖。推文 ID 仅用于任务内去重和恢复，不展示在文件名或 UI。

## 架构

- **Popup UI**：校验当前页面、保存采集开关、展示任务状态、控制开始/停止/下载/暂停/重试。
- **Service worker**：维护下载队列、限制并发、调用 Chrome 下载 API、持久化任务状态并汇总下载结果。
- **Document-start 内容脚本与页面桥接脚本**：在页面加载早期观察 X 请求返回的推文数据，提取图片原图 URL 和视频 variants；在采集状态下将符合筛选条件的标准化媒体记录发送给 service worker。
- **页面观察器**：观察推文卡片的出现，关联 URL、作者、推文时间和已捕获的媒体数据，处理 X 虚拟列表重新渲染。
- **本地任务存储**：以用户名和推文 ID 作为主键保存采集、下载和失败状态，确保重复滚动不重复收录并支持恢复。

## 媒体策略

- 图片下载 URL 使用 X 的原图参数，保留服务器提供的实际图片格式。
- 视频从同一媒体的 MP4 variants 中选取比特率最高的一项。
- 没有 MP4 variant、只有流媒体分片的视频标记为“无可用 MP4”，不会被错误记为完成。
- 媒体的去重键由推文 ID、媒体索引和规范化原始 URL 组成。
- 下载默认在采集完成后统一开始，使用有限并发，避免浏览器与站点的高并发压力。

## 状态和异常处理

- 未登录、受保护账号、页面不属于用户主页、未按提示刷新、尚未滚到最早内容等情况显示明确提示。
- 每个下载项有 `pending`、`downloading`、`completed`、`failed`、`unavailable` 状态。
- 下载失败保留失败原因和重试入口；完成项不会重复下载。
- 页面关闭、popup 关闭或浏览器重启后，本地记录保留；任务在下次打开相应主页时可继续。
- “全部”表示 X 对该浏览器会话实际返回且可访问的历史内容；X 的访问限制、删除内容、私密内容和速率限制不由扩展绕过。

## 权限与数据边界

- `downloads`：写入浏览器的默认下载目录。
- `storage`：保存任务、去重键和恢复状态。
- `scripting` / 内容脚本匹配：仅注入 `https://x.com/*` 与 `https://twitter.com/*`。
- 对 `*.twimg.com` 等 X 媒体域名申请最小必要访问权限。
- 不上传账号信息、Cookie、推文正文或下载记录；所有任务数据保存在本地 Chrome 配置中。

## 验收标准

1. 图片推文以原图下载，多图能生成连续文件名且不覆盖。
2. 含多个 MP4 variant 的视频选择最高码率版本。
3. 上下反复滚动、虚拟列表重渲染和同一媒体重复出现时，计数和下载清单不重复。
4. 关闭 popup 或重启浏览器后，待下载和失败项仍可恢复与重试。
5. 转推和回复开关能正确影响采集范围。
6. 受限视频和无法访问的内容显示可理解的原因，且不会伪造下载成功。
